# 三端联动最佳实现方案（exe / 云端 / APK）

> 状态：**方案设计稿，未改动任何代码**。
> 目标：三端数据互通；APK 界面简约、功能完善；exe 界面保持原状、尽量不新增内容。
> 依据：2026-10-12 对仓库源码与线上云服务的实测（命令见文末附录）。

---

## 0. 一页结论

1. **云服务就是一个标准 BaaS**：CORS 全开放（回显任意 Origin），鉴权只看 `X-Wb-Webapp-Access-Key` + JWT。此前"云端强制请求来源 == 发布域名"的判断**已被实测推翻**。
2. 因此**不需要"浏览器中转"**。exe 可以直接连云端数据面，双向读写。
3. 最优架构是**三端直连同一份 `documents` 数据**，而不是链式转接：
   - exe = 本机文件为准 + 双向同步
   - 云端页 = 零安装的在线查看/上传
   - APK = 移动查看/轻编辑（Capacitor 原生能力补齐）
4. exe 侧**几乎不用动 Rust**：`FileEntry` 已自带 `content_sha256` / `modified` / `content`，与云端 `content_sha` / `doc_mtime` 天然对齐；写入复用既有 `/api/save`、`/api/create-doc`、`/api/delete`。
5. exe 界面**零新增控件**：全部收进现有工具栏「云端」按钮那个面板里。
6. 唯一硬约束：**微信登录在 exe 内拿不到回调**（OAuth 要跳浏览器，会话落在发布域名的存储里）。exe 端以**验证码/密码登录**为准，微信引导至网页版/APK。

## 1. 现状诊断

### 1.1 三端能力矩阵

| 维度 | exe（Tauri 2） | 云端页 | APK（Capacitor 6） |
|---|---|---|---|
| 运行位置 | `http://127.0.0.1:<7321+>` | `mytemple-cloud.app.workbuddy.host` | WebView 加载云端页 |
| 后端 | Rust axum，约 70 个端点 | BaaS（auth + PostgREST + storage） | 无（即云端） |
| 数据源 | 本机文件系统（唯一真相源） | `documents` 表 | `documents` 表 |
| 独有能力 | 完整编辑器/图谱/AI/截图/录屏/导出/许可 | 无（只读为主） | Android 原生（未启用） |
| 与云端耦合 | 仅 `initCloudSync()` 一处 + `cloud-sync.js` 一个文件 | — | `server.url` 指向云端 |

**云端数据模型（实测 OpenAPI 取得，全库仅两张表）：**

```
documents
  id            int64
  owner_id      text
  workspace     text
  rel_path      text
  title         text
  content       text          -- 正文，Markdown 原文
  content_sha   text          -- 内容指纹（与 FileEntry.content_sha256 同义）
  bytes         int64
  doc_mtime     int64         -- 与 FileEntry.modified 同义
  tags          text[]        -- 已建字段，当前前端未使用
  deleted_at    timestamptz   -- 软删除，当前仅用于过滤
  created_at / updated_at

唯一约束：(owner_id, workspace, rel_path)
```

```
kb_meta
  owner_id      text
  display_name  text
  last_sync_at  timestamptz
  doc_count     int32
  client_ver    text
  created_at
```

### 1.2 关键实测：旧假设被推翻

对线上数据面直接发请求（`GET /.cloud/database/rest/v1/documents?select=id&limit=1`）：

| 探测项 | 实测结果 | 含义 |
|---|---|---|
| `Origin: http://127.0.0.1:7321` + access key | **200 `[]`** | exe 的源可直接访问数据面（空数组是 RLS 过滤匿名） |
| `Origin: https://evil.example.com` | 回显 `ACAO: https://evil.example.com` | **无 Origin 白名单**，CORS 完全开放 |
| `Origin: null` / `localhost:9999` | 同样回显 | 同上 |
| 预检 `OPTIONS` | **204**，`Allow-Methods: GET,POST,PUT,PATCH,DELETE` | 写请求也可跨域 |
| 不带 access key | **401 `invalid_client`** | 真正的鉴权依据 |
| `Vary: Origin` | 有 | 标准 CORS 实现 |
| 云端页响应头 | **无 `X-Frame-Options` / 无 CSP** | 可被 iframe 嵌入（备用手段） |

**结论**：安全边界在 `publishableKey` + JWT + 行级权限（RLS）上，**不在 Origin**。
现有 `handlers.rs::cloud_read_cors` 中间件与"浏览器中转"流程，是为一个不存在的限制付出的复杂度。

> 注：`cloud_read_cors` **不必删除**——它仍有独立价值（让浏览器里的网页版读本机只读数据）。但它不该是 exe 同步云端的主路径。

### 1.3 真正的断点（见图 1）

| 方向 | 现状 |
|---|---|
| exe → 云端 | 有，但绕：需浏览器 + 本机只读接口中转，且**只能上传、不能拉回** |
| 云端 → exe | **无** |
| 云端 ↔ APK | 有（APK 就是云端页） |
| exe → 本机 | 完整（本机 API） |
| exe ↔ APK | **无**（axum 只绑 `127.0.0.1`） |

## 2. 目标架构

### 2.1 设计原则

1. **单一数据中枢**：`documents` 表是三端交换的唯一契约，不引入第二种同步形态。
2. **本机优先**：exe 的文件系统仍是真相源，云端是镜像；冲突时以"本机不被静默覆盖"为底线。
3. **界面零膨胀**：exe 不新增工具栏按钮；APK 以云端页为底，只做原生增强。
4. **一端一前端**：APK 不另写一套 UI，继续用 `server.url` 加载云端页，避免双份维护。

### 2.2 形态（见图 2）

```
                云服务 BaaS（documents · kb_meta）
              ↗              ↑                ↖
        exe 桌面端        云端页面            APK
     本机优先·双向同步   在线查看·上传    移动查看·轻编辑
              ↘                               ↙
                局域网直连（可选，P3）
```

## 3. 分端实施方案

### 3.1 exe：最小改动清单（界面零新增）

**新增 1 个文件**

| 文件 | 作用 |
|---|---|
| `public/modules/cloud-client.js` | 云端 SDK 引导 + 登录态 + 双向同步内核 |

要点：
- 复用与云端页**同一份** SDK（`cloud/vendor/sdk/workbuddy-cloud-sdk.global.js`），避免两份实现漂移。
- 用 `scripts/vendor-cloud.mjs` 追加一个输出目标（`public/vendor/sdk/`），构建时同步。
- 走 `X-Wb-Webapp-Access-Key` + `Authorization: Bearer <token>`，端点 `/.cloud/database/rest/v1/documents`。
- 不自己实现 auth 流程，直接用 SDK 的 `sendOtp / verifyOtp / signInWithPassword`（已验证端点跨源可用）。

**改写 1 个文件**

| 文件 | 改动 |
|---|---|
| `public/modules/cloud-sync.js` | 面板按钮语义升级，**控件数量不变** |

现有 3 个按钮 → 保持 3 个，按登录态切换语义：

| 未登录 | 已登录 |
|---|---|
| 「登录云端」 | 「拉取云端更新」（云端 → 本机） |
| 「打开云端工作台」 | 「推送本机 → 云端」 |
| 「复制路径」 | 「打开网页版」 |

面板里增一行登录态文字（账号掩码 + 上次同步时间），不新增按钮。

**引入 2 行静态引用**（`public/index.html`）：

```html
<script src="/vendor/sdk/workbuddy-cloud-sdk.global.js?v=<当前戳>"></script>
<script src="/cloud-config.js?v=<当前戳>"></script>
```

> `cloud-config.js` 需从 `cloud/` 复制一份到 `public/`（内容同源同键），或由构建脚本统一产出。

**Rust 侧：理论零改动。** 复用既有端点：

| 用途 | 端点 | 请求体 |
|---|---|---|
| 列本机文件 | `GET /api/files` | — （返回 `{ok,data:FileEntry[]}`） |
| 读正文 | `GET /api/files/*path` | — |
| 写回正文 | `POST /api/save` | `{path, content, baseHash?}` |
| 新建文档 | `POST /api/create-doc` | `{parent, name}` |
| 删除 | `POST /api/delete` | 见 `delete_docs` |

**必须在三处同步的约定**（项目既有规则）：新增端点需同改 `handlers.rs` + `public/app.js` 的 `IPC_ROUTE_MAP`（第 747 行）+ `lib.rs` 的 `invoke_handler`。**本方案不新增端点，因此三处都不动。**

**缓存戳**：改 `public/` 静态文件后必须递增 `?v=`（`index.html` 四处 + `app.js` 两处，含 markdown-worker），当前为 `20261012-cloud-2`。

### 3.2 云端页：从"唯一入口"回归"网页版"

- 保留 `/vendor/` 自托管（不得回退到第三方 CDN）。
- 现有「一键推送（读本机）」保留，作为"没装 exe 时"的替代路径。
- 新增：识别 exe 同步写入的文档来源（可用 `kb_meta.client_ver` 或 `documents.tags` 打标），在列表里给出"来自本机/来自网页"的轻提示。
- 新增：`window.Capacitor` 渐进增强分支（见 3.3）。

### 3.3 APK：界面简约 + 功能完善

**保持 `server.url` 远程加载云端页**——这是"界面简约"的最优解：零 UI 重复维护，且自动跟随云端页更新。**绝不能改用 `server.hostname`**（会让同域数据面被本地资源服务器拦截）。

"功能完善"靠 **Capacitor 插件 + 云端页渐进增强**实现，不改云端页的视觉结构：

| 插件 | 补的能力 | 云端页挂点 |
|---|---|---|
| `@capacitor/app` | Android 返回键 → 视图回退，而不是退出应用 | `viewDoc → viewList → 退出` |
| `@capacitor/camera` | 拍照直接插入笔记（移动端核心价值） | 编辑器/上传面板 |
| `@capacitor/share` | 分享笔记到微信等 | 文档页底部 |
| `@capacitor/clipboard` | 复制正文/链接 | 文档页 |
| `@capacitor/filesystem` | 导出 .md 到手机存储 | 文档页 |
| `@capacitor/network` | 网络状态 → 自动切兜底页 | `offline.html` 逻辑 |
| `@capacitor/status-bar` / `splash-screen` | 观感（配色沿用暖色令牌） | 启动 |
| （可选）本地通知 | 同步完成提醒 | 同步流程 |

云端页里统一用一个判定：

```js
const NATIVE = !!window.Capacitor?.isNativePlatform?.();
```

**权限**：`AndroidManifest.xml` 目前只声明 `INTERNET`，需按插件补 `CAMERA`（并按需 `READ_MEDIA_IMAGES`），保持最小化。

## 4. 同步语义设计

### 4.1 增量（三个端一致）

1. 取两端清单：本机 `GET /api/files`（含 `content_sha256`、`modified`），云端 `select rel_path, content_sha, doc_mtime`。
2. 按 `rel_path` 求差集：
   - 仅一侧有 → 新增到另一侧
   - 两侧都有且 `content_sha` 相同 → 跳过（**不读正文**）
   - 两侧都有且不同 → 进入冲突判定
3. 正文按需懒取，分批 upsert（沿用云端页既有 `UPSERT_BATCH_MAX_DOCS=20` / `MAX_BYTES=1.2MB`）。

### 4.2 冲突

**判据**：`doc_mtime`（本机 `FileEntry.modified`） vs 云端 `updated_at`。

| 情形 | 处理 |
|---|---|
| 本机 mtime > 云端 updated_at | 本机新 → 推送覆盖云端 |
| 云端 updated_at > 本机 mtime | 云端新 → 拉取覆盖本机 |
| 时间接近（< 1 分钟）且 sha 不同 | **判为冲突**：本机文件保留原样，云端版本另存为 `<name>.conflict-<设备>-<时间>.md` |

**底线**：任何情况下**不静默覆盖本机**。拉取覆盖前先比对 `baseHash`（`/api/save` 已支持），若本机在读取后被改过则跳过并提示。

### 4.3 删除

`documents.deleted_at` 已存在但当前只用于过滤，未参与同步。建议：

- 拉取时：云端 `deleted_at` 非空 → **不删本机文件**，只在 UI 提示"云端已删除"。
- 推送时：本机消失的文件 → 标记云端 `deleted_at`（而非物理删除），可恢复。

> 这是"本机优先"原则的延伸：**云端删除不反向删本机**，避免误删不可逆。

## 5. 安全边界

| 项 | 设计 |
|---|---|
| 凭据 | 仅 `publishableKey`（公开键，无权限）+ 用户 JWT。**不得**在前端出现任何长期密钥。 |
| 数据隔离 | 由云端 RLS 按 `owner_id` 保证（实测：匿名查询返回空数组）。 |
| exe 会话存储 | SDK 固定用 `localStorage`，绑定 `http://127.0.0.1:<port>`。**端口漂移会导致会话丢失** → 属已知限制；缓解见 7.1。 |
| 本机只读接口 | `handlers.rs::cloud_read_cors` 保持现状：只挂 3 个只读 GET，写端点一个都不挂，来源不匹配不加头。 |
| 局域网直连（P3） | **必须** token 鉴权 + 二维码配对；默认关闭；只读优先。未经鉴权不得开放。 |

## 6. 实施顺序

### P1 — 打通主干（推荐先做）
1. `scripts/vendor-cloud.mjs` 追加输出到 `public/vendor/sdk/`。
2. 新增 `public/modules/cloud-client.js`（登录 + 双向同步）。
3. 改写 `public/modules/cloud-sync.js` 面板（3 按钮语义切换 + 登录态一行）。
4. `public/index.html` 引入 SDK 与配置；`public/vendor/` 与 `cloud-config.js` 就位。
5. 递增缓存戳；补契约测试（沿用 `tests/cloud-sync.test.js` 风格）。
6. **Rust 零改动**，无需重新编译安装包的功能性改动（但发版仍需重建）。

### P2 — APK 功能完善
7. 安装 Capacitor 插件（app / camera / share / clipboard / filesystem / network / status-bar）。
8. 云端页加 `NATIVE` 渐进增强分支（不改变视觉结构）。
9. `AndroidManifest.xml` 补最小权限；重建 APK 并归档。

### P3 — exe ↔ APK 局域网直连（可选，价值最高但成本也最高）
10. exe 侧增加**可选**的局域网监听（与 `127.0.0.1` 分开的第二 listener，或改绑策略）+ token 鉴权 + 二维码配对。
11. APK 扫码后直连，直接读写电脑上的知识库（拍照即入库）。
12. 默认关闭，设置里显式开启。

### P4 — 同步语义收口
13. 冲突副本、`deleted_at` 墓碑同步、`kb_meta` 记录 `client_ver` 与 `last_sync_at`。

## 7. 风险与未验证项

### 7.1 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| SDK 会话绑 `localStorage`（含端口） | 7321 被占用 → 端口漂移 → 掉登录态 | 固定 `MYTEMPLE_PORT`；或把 `localStorage` 代理到 Rust 存储（key 白名单，只拦 SDK 的键） |
| 微信登录需 OAuth 跳转 | exe 内拿不到回调会话 | exe 只提供验证码/密码；微信引导到网页版/APK |
| 写接口并发 | 三端同时改同一篇 | LWW + 冲突副本（见 4.2）；**绝不静默覆盖本机** |
| 大库同步耗时 | 数千篇 Markdown 首次全量 | 沿用分批 upsert + 进度/取消，已具备 |

### 7.2 必须在真机验证的项（沙箱无法覆盖）

- exe 内登录（验证码/密码）→ 推送 → 云端页可见 → 拉回本机的**完整往返**。
- APK 真机：安装、登录、上传、返回键、拍照插入、分享。
- 三端并发编辑同一篇时的冲突副本行为。

### 7.3 尚未验证的假设

- exe 端 SDK 初始化在 `http://127.0.0.1:<port>`（非 https 但属 secure context）下的**全部**行为——已验证数据面跨源 200，但未跑真实登录换取 JWT。
- 云端平台是否对"同一 publishableKey 在非发布域名使用"另有策略限制（实测只有 CORS 与密钥校验，未见域名绑定）。

## 附录：实测命令

```bash
E="https://mytemple-cloud.app.workbuddy.host"
K="<publishableKey>"

# 1) 跨源可读（返回 200 [] 而非 401）
curl -s -D - "$E/.cloud/database/rest/v1/documents?select=id&limit=1" \
  -H "Origin: http://127.0.0.1:7321" -H "X-Wb-Webapp-Access-Key: $K"

# 2) 无 Origin 白名单（回显任意源）
curl -s -o /dev/null -D - "$E/.cloud/database/rest/v1/documents?select=id" \
  -H "Origin: https://evil.example.com" | grep -i access-control-allow-origin

# 3) 预检允许写方法
curl -s -o /dev/null -D - -X OPTIONS "$E/.cloud/database/rest/v1/documents" \
  -H "Origin: http://127.0.0.1:7321" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization,content-type"

# 4) 表结构
curl -s "$E/.cloud/database/rest/v1/" -H "X-Wb-Webapp-Access-Key: $K"
```

复现时注意：沙箱内需走代理，`cdn.jsdelivr.net` 在此网络下 TLS 被重置（已自托管规避）。
